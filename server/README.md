# SIGNOO server (B11-B16)

FastAPI + SQLAlchemy service implementing ingest/review, the training trigger,
the model registry + promotion gate, the knowledge base, fleet control, and the
role-scoped console API. Companion docs: `docs/SYSTEM_DESIGN.md` §3,
`docs/REQUIREMENTS.md` §3.4/§5.3/§4.5/§3.3, `docs/API_CONTRACTS.md`.

## Environment

Windows dev machine. The `python` on PATH is unrelated to this project — use a
dedicated venv built from
`C:\Users\Abdel\AppData\Local\Programs\Python\Python311\python.exe`:

```
"/c/Users/Abdel/AppData/Local/Programs/Python/Python311/python.exe" -m venv server/.venv
server/.venv/Scripts/python.exe -m pip install -r server/requirements.txt
```

**Windows console encoding.** `ml/*.py` prints Arabic labels; Windows' cp1252
console default crashes on them. `server/main.py` reconfigures `stdout`/`stderr`
to UTF-8 at import time, and every subprocess call into `ml/` (`server/training.py`,
`server/tests/test_gate.py`) sets `PYTHONIOENCODING=utf-8` for the child process.
If you invoke `ml/*.py` directly yourself, set that env var first:
`$env:PYTHONIOENCODING = "utf-8"` (PowerShell) or `export PYTHONIOENCODING=utf-8` (bash).

## Database

**Postgres via Docker Compose is the intended backend** (`server/docker-compose.yml`):

```
docker compose -f server/docker-compose.yml up -d
$env:SIGNOO_DATABASE_URL = "postgresql+psycopg2://signoo:signoo_dev_password@localhost:5432/signoo"
```

**Docker was not available in this dev sandbox** (`docker`/`docker-compose` not on
PATH) — this was verified, not assumed, before falling back. Everything in this
project (`server/db.py`, every model in `server/models.py`) uses only
SQLAlchemy-generic column types, so the same code runs unmodified against
Postgres; `psycopg2-binary` is pinned in `requirements.txt` for when it's
available. Without `SIGNOO_DATABASE_URL` set, the app falls back to a local
SQLite file (`server/signoo_dev.db`) — this is what was actually exercised and
tested in this environment. **Postgres itself was not verified; say so plainly
rather than claiming otherwise.**

### Migrations

```
server/.venv/Scripts/python.exe -m alembic -c server/alembic.ini upgrade head
```

The initial migration (`server/alembic/versions/76adb2b2864e_initial_schema.py`)
was autogenerated against the SQLAlchemy models and applies cleanly to a fresh
SQLite DB (verified). Because it was generated from generic column types, it
should apply equally to Postgres, but that specific path is untested here.

For quick local iteration (tests, first run), `server/main.py`'s startup hook
also calls `Base.metadata.create_all()` directly — a shortcut for dev/test, not a
replacement for Alembic in a real deployment.

## Running the server

```
server/.venv/Scripts/python.exe -m server.seed admin@signoo.dev <password>   # first admin
$env:SIGNOO_JWT_SECRET = "<pick something>"
server/.venv/Scripts/python.exe -m uvicorn server.main:app --reload
```

Then create reviewer/engineer/operator accounts via `POST /auth/users` (admin
token required) and log in via `POST /auth/login` to get a JWT for the other
endpoints.

Verified manually against a running instance on this machine: `/health`,
`/auth/login`, `POST/GET /kb` (including the unrenderable-word warning and the
Arabic round-trip through the API — confirmed via a Python/httpx client, since
Git Bash's own shell mangles non-ASCII in `curl -d` arguments before they ever
reach the server; that mangling is a terminal artifact, not a server bug),
`POST /fleet/kiosks/register`, `GET /fleet/kiosks`.

### Simulated kiosk (B15)

server/.venv/Scripts/python.exe server/scripts/simulate_kiosk.py --heartbeats 3 --interval 2

## Tests

```
$env:SIGNOO_JWT_SECRET = "test-secret"
server/.venv/Scripts/python.exe -m pytest server/tests -q
```

26 of the 30 tests are fast (SQLite in-memory-per-test, no subprocess): auth,
ingest/review queue ordering and decisions, KB CRUD + unrenderable-word warning,
fleet registration/heartbeat/rollout, registry sequencing (candidate → shadow →
promoted/rejected, champion-stays-on-rejection).

**`server/tests/test_gate.py` is the explicit ROADMAP.md Phase 1/4 exit
criterion** — it generates a synthetic dataset (`ml/make_synthetic.py`), trains
one model properly (60 epochs) and one deliberately sabotaged (1 epoch, same
data/split/seed — so the only variable is training quality, not a data
difference), evaluates both with the real `ml/evaluate.py`, and asserts
`server/gate.py`'s `evaluate_gate()`:

- rejects the sabotaged candidate, specifically on the top-1-accuracy criterion
  (`test_gate_rejects_sabotaged_candidate`);
- does **not** reject the properly-trained model compared against itself as
  champion (`test_gate_does_not_reject_good_candidate_on_accuracy`);
- rejects on latency alone when the budget is exceeded, and rejects when the
  shadow-run period hasn't completed, independent of accuracy
  (the remaining two tests).

**Verified: all 4 pass when `test_gate.py` is run on its own** (`pytest
server/tests/test_gate.py -q`, ~4 minutes — real training, not mocked).

**Observed flakiness, root-caused, not hidden:** running the *entire* suite while
a separate `uvicorn` dev instance was also running (manual API smoke-testing, see
above) hit `RuntimeError: not enough memory` inside PyTorch's CPU allocator
partway through `test_gate.py`'s training subprocess — real host memory pressure
in this sandbox from the extra process, not a bug in the gate or training code.
With no competing server process, the full 28-test suite (including
`test_gate.py`) passed cleanly and deterministically, twice in a row, at ~4-4.5
minutes total. If running in CI, don't share a runner with another live memory-
hungry process; `test_gate.py` can run in its own job if that's easier to guarantee.

## Known gaps (documented, not silently skipped)

- **B12 cadence**: `POST /training/trigger` is a manual job, not FR-L5's live
  3-day cron — there is no reviewer throughput yet to feed a real schedule. The
  export step (`server/training.py::export_validated_manifest`) refuses to run
  below 3 distinct validated signers (DR-4's signer-independent split needs at
  least one signer per split) and raises a typed `InsufficientDataError` (422),
  which is the expected steady state right after launch.
- **False-accept rate (DR-6 criterion 5)**: `ml/evaluate.py` has no non-signing
  negative set to measure this against yet. `server/gate.py` treats a missing
  measurement as "not measured, does not block" rather than fabricating a
  number — see the comment in `evaluate_gate()`. Building that negative set is
  ml/ follow-up work, not something this server layer can manufacture.
- **Live shadow-run monitoring**: `POST /registry/{version}/shadow-complete`
  recomputes the gate with `shadow_run_complete=True` but does not itself watch
  live traffic for degradation during the window (FR-L7/DR-6 #7) — there is no
  live fleet traffic to watch yet. The flag is operator-asserted for now.
- **Kiosk auth**: `/ingest/sessions` and `/fleet/kiosks/*` have no
  kiosk-identity check beyond a soft `kiosk_id` lookup — `SYSTEM_DESIGN.md` §5
  specifies mTLS at the transport layer for this, which this dev server does not
  terminate itself.
- **KB sharing with kiosk/**: every KB write also rewrites
  `kiosk/data/knowledge_base.json` in full (`server/kb.py::sync_kiosk_kb_file`),
  so kiosk B7 can read it directly — this is the dev-simulation shortcut named
  in the task; a real deployment syncs this over the network (mTLS,
  store-and-forward) instead of sharing a file path between two processes.
- **Rollback (`POST /registry/{version}/rollback`)** marks the model version
  `rolled_back` but does not itself revert fleet kiosks' `current_model_version`
  — pair it with a new `POST /fleet/rollouts` targeting the previous champion to
  actually move traffic back.
- **`/auth/users` is admin-gated**, including for the very first user — creating
  the first admin on a fresh database is `server/seed.py` (a script, not an
  endpoint), since no admin token can exist yet to authorize the first call.

## Layout

```
server/
  main.py            FastAPI app, router wiring, startup
  config.py          Settings resolved once from the environment
  db.py              SQLAlchemy engine/session (Postgres or SQLite)
  models.py          ORM: User, SessionUpload, ReviewItem, ModelVersion,
                      KBEntry, Kiosk, Rollout
  schemas.py          Pydantic shapes matching docs/API_CONTRACTS.md
  auth.py            JWT + role-based least-privilege dependency
  gate.py            B13's 7-criterion promotion gate (pure function)
  training.py        B12: DB-validated-data -> manifest/split -> ml/train.py
  kb.py              Unrenderable-word check + kiosk/ file sync
  seed.py            First-admin bootstrap script
  routers/           auth, ingest, review, training, registry, kb, fleet
  alembic/           migrations (initial schema autogenerated + verified)
  scripts/
    simulate_kiosk.py  stand-in for a physical kiosk (B15)
  tests/             pytest suite, incl. test_gate.py (see above)
  docker-compose.yml Postgres for local dev
  requirements.txt   pinned, exactly what's installed in server/.venv
```
